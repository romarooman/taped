Дата: 14 октября 2026. Хост: Windows 10, build 19045. Проверяется production-сборка на локальном HTTP-сервере, а не JSDOM. Playwright 1.64.1.

## Сценарии

На каждой из восьми конфигураций запускаются пять тестов:

1. Открытие десяти маршрутов, наличие контента, загрузка видимых non-lazy изображений. Снимки главной, эксперта и услуги.
2. Desktop/mobile меню: услуги → контакты, URL, закрытие мобильного меню.
3. Выбор тарифа и цены, ввод трёх полей формы, управление фотогалереей.
4. Слайды эксперта, блокировка на время перехода и освобождение прокрутки после последнего слайда.
5. Ширина document/body на десяти маршрутах после окончания анимации.

Во всех этих тестах собираются необработанные JavaScript-исключения. У мобильных профилей часть touch-сценариев использует синтетические TouchEvent; это проверка браузерных обработчиков, не нативного поведения ОС. У мобильного WebKit освобождение wheel-события и программная прокрутка проверяются отдельно, поскольку mouse.wheel API в таком профиле не поддерживается.

Два дополнительных Android-профильных теста используют `Input.dispatchTouchEvent` через Chromium DevTools Protocol: переключение слайдов эксперта и прокрутку FAQ. Эти жесты проходят через систему ввода браузера; физического телефона при этом нет.

## Подтверждённая ошибка: мобильная прокрутка FAQ

**Приоритет: высокий для мобильного UX.**

Воспроизведение в профиле Pixel 7:

1. Открыть `/service`.
2. Свайпнуть вверх для перехода к FAQ.
3. После завершения анимации свайпнуть вверх внутри списка вопросов, пока он ещё может прокручиваться.

Ожидается прокрутка списка вопросов с сохранением FAQ. Фактически открывается следующая секция — фотогалерея; FAQ исчезает. Тест `browser touch input scrolls FAQ without changing the active page` падает на проверке сохранения заголовка FAQ.

Причина по коду: глобальный `src/Components/PageSlider/hooks/useTouch.js` не учитывает `data-inner-scroll` и вызывает next по любому достаточно длинному вертикальному жесту. Дополнительно `touch-action: none` у `.viewport` в `PageSlider.module.css` запрещает нативную прокрутку потомков. Нужна согласованная правка обработки жестов и CSS. В рамках этой проверки поведение приложения не менялось; регрессионный тест оставлен падающим, чтобы проблема не скрывалась.

Скриншот, trace и DOM ошибки находятся в `test-results/android-touch-browser-touc-ee91a-ut-changing-the-active-page-android-pixel-emulated/` и в HTML-отчёте.

## Запуск

```powershell
npm.cmd ci
$env:PLAYWRIGHT_BROWSERS_PATH = Join-Path (Get-Location) '.playwright-browsers'
npx.cmd playwright install chromium firefox webkit
npm.cmd run build
npm.cmd run test:browser
npm.cmd run test:browser:report
```

Для проектов windows-chrome/windows-edge нужны установленные Chrome и Edge. Все браузеры запускаются headless. Тесты используют сервер `scripts/serve-test-build.cjs`, который слушает только 127.0.0.1:4173 и поддерживает SPA fallback.

Если ограниченное Windows-окружение мешает завершить дочерний сервер, запустить его отдельно: `node scripts/serve-test-build.cjs`, затем в другом терминале установить `$env:E2E_REUSE_SERVER='true'` и выполнить тесты. Firefox в sandbox зависал до открытия страницы; вне sandbox базовые проверки выполнились. Это проблема окружения, а не обнаруженная ошибка приложения.

Артефакты: `playwright-report/index.html`, `browser-results.json`, `test-results/`. Команда `node scripts/summarize-browser-results.cjs` создаёт компактную сводку и извлекает скриншоты в `browser-evidence/`. Артефакты исключены из git.

## Ограничения результата

Успешная проверка ширины document/body не исключает обрезанный внутренний контент: приложение активно использует overflow:hidden. Это не полный визуальный regression или аудит доступности. Не проверялись экранная клавиатура настоящего телефона, динамическая адресная строка Safari, safe-area, ландшафтная ориентация, медленная сеть и реальное воспроизведение Vimeo. Доставка заявок/чата остаётся не реализована, как описано в [TESTING.md](TESTING.md).
